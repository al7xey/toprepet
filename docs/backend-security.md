# Безопасность и архитектура backend

Проверка ветки `design/home-mockup`, 05.11.2026. Это проверяемые меры защиты и границы системы, а не гарантия отсутствия всех уязвимостей. Доступа к рабочей инфраструктуре, её данным, настройкам Supabase и настоящим платёжным операциям в этой проверке нет.

## Архитектурное решение

Сохранён модульный монолит Django/DRF с PostgreSQL: accounts, tutors, lessons, requests_board, chats, payments, reviews. Для текущего продукта общая транзакция и ограничения БД проще и надёжнее распределённых транзакций между микросервисами. HTTP-граница проверяет аутентификацию, роль и форму входного объекта; доменные сервисы управляют переходами состояния, владением объектом и блокировками; ORM передаёт значения отдельно от SQL; PostgreSQL защищает инварианты независимо от HTTP.

Общие механизмы находятся в core: разрешения, ошибки, лимиты, доверие к прокси, журнал событий. PrivateDocumentStorage хранит приватные документы и вложения отдельно от публичных аватаров. Frontend не определяет права доступа или финансовое состояние.

## Защиты и проверенные сценарии

- **SQL injection.** Поиск и JSON-выражения используют параметры ORM. Динамические фрагменты ArrayIncludes/ArraySubjectMatches состоят из выражений компилятора Django; пользовательские значения остаются в params. Тесты вводят UNION/DROP/комментарии/pg_sleep и проверяют фактический SQL, отсутствие выдачи чужих данных и изменения пользователей. Поля сортировки, размеры страницы и курсоры валидируются. Это не разрешение добавлять raw SQL со строковой подстановкой.
- **Доступ.** Новые API по умолчанию требуют сессию. Публичные endpoints явно используют PublicAPIView. Администратор и репетитор имеют отдельные базовые классы. Неактивная сессия отклоняется. Чужие уроки, переписки, изображения и документы не выдаются по известному ID. Самостоятельная передача role/is_staff/is_superuser не повышает права.
- **Сессии и CSRF.** HttpOnly, SameSite=Lax, Secure в production; вход меняет session key, выход отзывает сессию, сброс пароля инвалидирует прежние сессии. Для небезопасных запросов проверяются точный Origin и JSON/multipart; cookie-запрос без Origin запрещён. HTTPS-заголовок принимается только от явно доверенного прокси. Сайт и API должны быть на одном browser site, например toprepet.ru/api.toprepet.ru; для другого размещения нужна отдельная схема cookie/CSRF.
- **Пароли.** Максимум 128 символов ограничивает вычислительное злоупотребление; минимум 8, запрет распространённых и полностью цифровых новых паролей. Существующие пароли продолжают работать. PBKDF2 используется вне pytest; MD5 разрешён только тестовым настройкам. Email-токен случайный, одноразовый, с TTL, в БД хранится SHA-256. Смена пароля перечитывает пользователя под блокировкой. Сохранение профиля изменяет только разрешённые поля и не восстанавливает старый хеш пароля.
- **Перебор и нагрузка.** Общие атомарные счётчики в PostgreSQL работают между процессами; очистка локального cache их не сбрасывает. Есть лимиты anonymous/user/auth/upload/message/report и Retry-After. Идентификаторы buckets — HMAC, без открытых IP. Просроченные buckets удаляет run_jobs. Недоверенный X-Forwarded-For не меняет ключ лимита. Ограничены размер JSON, число multipart-полей и файлов, фактический поток файла, размеры изображений, количество документов и длины команд.
- **Загрузка файлов.** Изображения декодируются и перекодируются без EXIF. Документы допускают изображения и PDF с проверкой оболочки; PDF выдаётся attachment с серверным именем. Проверка оболочки PDF не заменяет антивирус. Файлы приватного хранилища имеют права 0600, каталоги 0700; `.url` запрещён. Доступ к документу — владелец/администратор; к фото чата — участник. Проверка документа администратором отдельна от публикации анкеты; документы опубликованных анкет тоже попадают в очередь.
- **Ошибки и утечки.** Необработанные API-ошибки возвращают общий JSON без SQL/traceback/секретов. Для корреляции генерируется X-Request-ID; журналирует класс ошибки и ID, а не тело запроса. Ответы API no-store, nosniff, CSP и защита от встраивания. Gunicorn access log не пишет query string с токенами. Без SMTP production не выводит email-токены в консоль: операции отправки отвечают 503.
- **Конкурентность.** Бронь сериализуется по ученику, затем репетитору; перенос — по репетитору, затем уроку. Блокировки родительских User/Tutor используют FOR NO KEY UPDATE, чтобы не блокировать обычные FK-ссылки. Связанные записи не блокируются неявно через JOIN. Спор — порядок урок → спор; чат — блокировка Conversation перед изменением сообщений/счётчиков. Агрегат рейтинга сериализуется по репетитору. Проверки сроков повторяются под блокировкой; автозавершение проверяет прежние start/duration/status.
- **Инварианты БД.** PostgreSQL exclusion constraint запрещает пересечение активных уроков репетитора; смежные интервалы допустимы. Есть ограничения длительности/сумм/статусов, уникальности ключа бронирования и единственной основной карты. Ключ бронирования ограничен и проверяет отпечаток команды. Новые ID имеют 128 случайных бит. SQLite оставлен для разработки, с IMMEDIATE-транзакциями; production требует PostgreSQL.
- **Чаты.** GET не изменяет прочитанность. История выдаётся страницами до 100 сообщений; frontend умеет загружать предыдущие. Отдельное подтверждение чтения привязано к последнему реально полученному сообщению и не скрывает новое сообщение, пришедшее после страницы.
- **Контейнер и CI.** Код принадлежит root, процесс работает как UID 10001; writable media отделены. Docker context исключает .env, локальные БД и загрузки. CI проверяет сборку и UID контейнера, Python imports, Bandit medium/high, production pip-audit, PostgreSQL, контракт и браузер.

## Обязательные действия при обновлении существующего сервера

Изменение ветки не меняет production. Выполнить обновление в согласованное окно с резервной копией БД, публичных и приватных файлов и проверенной процедурой восстановления.

1. Закрыть прямой доступ к gunicorn; TLS завершается на доверенном ingress. До открытия API запретить статическую выдачу `/media/documents/` и любой PRIVATE_MEDIA_ROOT. Пример — `backend/deploy/nginx-security.conf.example`. Ограничить размер/время запросов и соединения на ingress. Удалить старые приватные файлы из CDN/cache после переноса, если они там были.
2. Задать DEBUG=0, длинный случайный SECRET_KEY, PostgreSQL DATABASE_URL, точные ALLOWED_HOSTS/ALLOWED_ORIGINS, HTTPS SITE_URL, SMTP EMAIL_URL. Cookie лучше оставить host-only для API; общий SESSION_COOKIE_DOMAIN не требуется для fetch с credentials. TRUSTED_PROXY_CIDRS содержит только реальные адреса непосредственного ingress; запретить прямой вход в API в обход него.
3. PRIVATE_MEDIA_ROOT расположен вне MEDIA_ROOT и любого web root. При контейнерном запуске подключить отдельный сохраняемый volume с правами UID 10001. Compose — только локальная демонстрация с DEBUG=1 и демонстрационным паролем БД; не production-шаблон.
4. Владелец PostgreSQL предварительно разрешает/устанавливает btree_gist. Миграционный пользователь имеет DDL-права; runtime-пользователь их не имеет. До миграции устранить исторические пересечения активных уроков и дубликаты primary-карт/ключей брони вручную по бизнес-решению. Миграции не удаляют эти данные автоматически.
5. Выполнить `python manage.py migrate`, затем `python manage.py secure_documents` и `python manage.py secure_chat_attachments`. Команды копируют локальные файлы, сверяют SHA-256 и удаляют публичный оригинал только после commit. Неизвестные пути, несовпадающие копии и внешние URL требуют ручной проверки; сетевого скачивания по URL из БД нет. Недоступные legacy chat images до переноса намеренно не получают публичный fallback.
6. Запустить `python manage.py check --deploy --fail-level ERROR`; проверить `/ready`, вход, бронь, приватную загрузку/скачивание и запрет доступа посторонним. `/health` проверяет процесс, `/ready` — доступность БД. В production запросы БД ограничены statement_timeout=5000ms и lock_timeout=3000ms; для планового DDL при необходимости отдельно задать DB_STATEMENT_TIMEOUT_MS=0/DB_LOCK_TIMEOUT_MS=0, затем вернуть лимиты runtime.
7. Запускать `python manage.py run_jobs` раз в минуту; контролировать ошибки, длительность и heartbeat задания. Настроить сбор событий SecurityEvent во внешнее хранилище и политику хранения. Таблица приложения не защищает журнал от администратора самой БД.

## Границы, требующие отдельной интеграции

Платежи по умолчанию disabled в production. FakeProvider не обрабатывает настоящие деньги. Перед включением оплаты нужны hosted fields, подписанные webhooks, outbox/журнал операций с уникальными ключами провайдера, повторная доставка и сверка. Транзакция PostgreSQL не откатывает внешний перевод или отправленное SMTP-письмо. Отправка почты пока синхронная с timeout; для надёжной доставки нужна очередь/outbox и повторные попытки. Яндекс ID и персональные видеокомнаты пока не реализованы.

Инфраструктурные меры: MFA/SSO для администраторов, внешняя защита от DDoS и массового перебора, антивирус/изоляция просмотра документов, шифрование дисков/копий, ротация секретов, минимальные права БД, мониторинг и регулярное восстановление резервной копии. RLS/Storage policies отдельного Supabase-блога проверяются в его проекте. Нужны нагрузочные тесты с целевыми SLO; длинные истории платежей/финансов/админские списки ещё требуют общей пагинации по согласованному API.

Текущие регрессионные проверки перечислены в `docs/hardening.md`. Автотесты и сканеры подтверждают конкретные сценарии и известные зависимости на дату проверки; независимый pentest и проверка реального окружения остаются отдельными работами.
